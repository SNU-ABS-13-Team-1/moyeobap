# Supabase 응답량 진단

서버 환경 변수 `SUPABASE_EGRESS_METRICS=1`을 설정하면 서버 Supabase 클라이언트가
요청당 `supabase_response` JSON 로그를 남긴다. 미설정이면 응답 본문 복제나 계측은
실행하지 않는다. Vercel 환경 변수 변경은 이후 배포부터 적용된다.

- `resource`: 테이블 또는 RPC 경로. 쿼리 문자열·사용자 ID·토큰·본문은 기록하지 않는다.
- `source`: admin(공통 서버 데이터), session(사용자 세션), proxy(세션 갱신).
- `decodedBodyBytes`: 서버가 받은 압축 해제 후 본문 크기. Supabase 청구 바이트와
  동일하지 않으며, DB 내부 스캔량이나 브라우저 응답 크기도 아니다.
- `method`, `status`: HTTP 메서드와 상태 코드.

`resource`별 로그 수와 바이트 합계를 비교한다. 어플라이는
`rest/v1/rpc/moyeo_apply_state`, 헤더는 `pots`, `pot_participants`, `message_reads`
등을 호출한다. 공통 테이블은 여러 API가 사용하므로 이것만으로 호출 페이지를
확정하지 말고, Vercel 요청 로그와 재현 시점을 함께 확인한다.

진단 중에는 응답 복제와 로그 비용이 추가되므로 짧은 관측 기간 후 변수를 제거한다.
진단 종료 시각을 운영자가 정한다. Realtime·브라우저 직접 요청·백업 연결은 이 계측에
포함되지 않는다. Supabase 일별 서비스 사용량과 대조한다.

## 검증 절차

1. 어플라이에 로그인하고 최초 조회·수동 새로고침·저장을 각각 수행한다.
2. 목록은 진입/새로고침/저장 뒤에만 조회되는지 확인한다.
3. 헤더 폴링에서 `pots`는 공개 요약 컬럼, `pot_participants`는 본인 행,
   `messages`는 팟별 최신 작성자·시각만 조회하는지 확인한다.
4. 타인의 팟 메시지가 unread에 섞이지 않는지, 참여 후·읽음 후 상태를 확인한다.
5. 오래된 참여 팟도 알림 집합에 남는지 확인한다. 알림 조회는 최근 60개 팟 제한을
   재사용하지 않는다. 조회에는 PostgREST의 서버 행 상한이 적용되므로 참여 팟이
   그 상한에 도달하는 운영 규모에서는 별도 페이지네이션이 필요하다.
6. 변경 전후 같은 이용 시간·요청 횟수에서 바이트 합계를 비교한다.

이번 변경은 SQL migration이 필요하지 않다. 헤더 조회는 읽기만 수행하며 팟을
마감 상태로 저장하지 않는다. 기존 팟 목록/상세의 상태 전환 동작은 유지된다.
