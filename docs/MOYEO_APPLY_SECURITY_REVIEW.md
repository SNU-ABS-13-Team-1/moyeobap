# 모여 어플라이 보안 점검 — 2026-10-18

대상: `feat/apply-reentry-name-privacy`의 코드와 로컬 마이그레이션.
운영 Supabase·실제 로그인 세션·운영 배포는 이번 검증 대상에 포함하지 않았다.
검증한 로컬 경로에서 미제출/미정 사용자의 목록 열람이나 비공개 이름의 직접
반환을 허용하는 추가 우회 경로는 발견하지 못했다.

## 발견 및 보완

| 항목 | 조건과 영향 | 조치 |
| --- | --- | --- |
| 구버전 DB 응답 전달 | 새 앱을 DB보다 먼저 배포하면 예전 RPC의 실제 이름 목록이 그대로 API를 통과할 수 있었음 | RPC 응답에 `privacyVersion: 1`을 추가하고, 버전이 없거나 다르면 API가 내용을 반환하지 않고 503 처리 |
| 사용자 ID에 따른 동률 정렬 | 비공개 행의 순서가 다른 기능에서도 쓰는 사용자 ID 순서에 의존했음. ID와 참여자 집합을 알고 있으면 대조의 단서가 될 수 있음 | 사용자 ID와 무관한 난수 `private_sort_key`를 DB에만 저장하고 동률 정렬에 사용. API에는 키를 반환하지 않음 |

구버전 DB에서 보호를 완성하려면 마이그레이션 적용이 필수다. API의 응답 차단은
직접 Supabase RPC 호출까지 대체하지 않는다. 따라서 문서의 DB 먼저 적용 순서를
유지한다. 응답 버전 검사는 DB 인증을 대신하지 않으며 앱/DB 배포 불일치를 감지한다.

## 실행한 검증

- 실제 프로필 마이그레이션과 Apply 마이그레이션 전체를 PGlite 0.5.8에 적용했다.
  `auth.users`와 JWT의 `auth.uid()`만 테스트 대역이며, 프로필 RLS와 Apply 함수는
  저장소 SQL 그대로 사용했다.
- 기존 확정 사용자의 지망·석차·수정 횟수·확정 상태가 보존되고 이름이 기본
  비공개로 전환되는 것을 마이그레이션 전후로 비교했다.
- `moyeo_apply.sql`, `moyeo_apply_confirmation.sql`, `moyeo_apply_privacy.sql`,
  `moyeo_apply_security.sql` 모두 통과했다.
- 비로그인·미제출·미정 사용자의 목록 차단, 익명 RPC 권한 차단, 테이블 직접
  조회·삽입·수정·삭제 차단과 다른 사용자 프로필 조회·수정 차단을 확인했다.
- NULL·중복·빈 값·비활성 기업·0부터 시작하는 배열·2차원 배열·SQL 구문 형태의
  문자열을 DB에 직접 전달해도 제출을 만들거나 열람 권한을 얻지 못했다.
- 이름 기본 비공개, 명시적 공개/해제, 확정 후 이름 설정 변경, 수정 횟수 보존,
  오래된 요청 거절과 멱등 재시도를 확인했다.
- 비공개 프로필 이름 및 사용자 ID를 바꿔도 목록의 값과 순서가 달라지지 않았다.
  석차를 등록하지 않은 조회자의 응답에는 석차 필드와 석차 기반 순서가 없었다.
- 함수 카탈로그에서 익명 실행 권한, 안전한 `search_path`, `SECURITY DEFINER`,
  사용자 ID를 받는 인자 부재와 구버전 저장 오버로드 제거를 검사했다.
- 실제 API 핸들러를 인증·DB 대역과 함께 실행했다. GET/PUT/POST/PATCH의 비로그인
  401, 오류를 포함한 `private, no-store`, 잘못된 요청 400, 구버전 응답 503,
  사용자 ID·공개 여부·수정 횟수 위조 필드가 RPC 인자로 넘어가지 않는 것을 확인했다.
  DB 오류의 상세 메시지나 이름·토큰이 응답에 포함되지 않는 것도 확인했다.
- 실제 `ApplyClient`의 빈 재입력 폼, 5지망 저장 후 참여, 기본 비공개와 공개 선택을
  jsdom에서 확인했다. 관련 JS/TS 테스트 14개, TypeScript, 변경 파일 ESLint를 통과했다.
- 두 클라이언트 대역으로 탭 숨김·복귀·저장 신호·실패한 재조회·지연 응답·응답 유실을
  검증했다. 목록과 석차 권한은 무효화 후 새 조회가 성공해야 복구되고, 탭 사이에는
  변경 신호만 전달했다.

SQL 검사는 반드시 임시 DB에서 실행한다. 각 검사 파일은 끝에 롤백한다.
PGlite 검증은 실제 Supabase JWT 서명 검증, PostgREST/GraphQL 네트워크 설정,
Realtime publication, 여러 PostgreSQL 연결의 동시 요청을 검증한 결과는 아니다.
인증은 기존 사용자 JWT 클라이언트를 사용하며 Apply 경로에는 서비스 역할 클라이언트가 없다.

## 남는 정책상 한계

- 특정 조직으로 가입을 제한하지 않는다. Google 계정으로 임의의 유효한 5지망을
  제출해도 목록을 볼 수 있다. 입력한 지망의 진실성이나 실제 캡스톤 참여 자격은
  검사하지 않는다.
- 석차도 본인 입력이다. 임의의 양수를 입력하면 석차 공유자로 인정된다. 실제 성적표와
  대조하지 않으므로 이 조건은 상호 입력 규칙이지 실제 석차 인증이 아니다.
- 이름을 숨겨도 이미 알려진 석차·지망 조합으로 사람을 추측할 수 있다. 이전에
  공개되어 복사·저장된 이름을 회수하거나, 공개 당시 지망과의 연결을 지울 수는 없다.
- 이름을 비공개로 바꿔도 다른 기기에서 이미 받은 응답은 회수되지 않는다. 다른
  참여자의 열린 화면은 새로고침·탭 복귀 등 다음 조회에서 반영된다. 상시 폴링이나
  전체 사용자에게 변경을 전파하는 구독은 현재 범위에 없다.
- 운영 적용 여부와 실제 배포 권한 설정은 이번 로컬 검증으로 보장하지 않는다.
