# 모여 어플라이 적용 안내

제품 규칙은 [AGENTS.md](../AGENTS.md)의 14절에서 관리합니다.

## 데이터베이스 적용

기존 모여밥 Supabase 프로젝트의 SQL Editor에서
[`20261006000000_moyeo_apply.sql`](../supabase/migrations/20261006000000_moyeo_apply.sql)
전체를 한 번 실행한 뒤 이 브랜치의 앱을 배포합니다. 기존 `auth.users`와
`public.profiles`를 전제로 하며, 새 환경 변수나 외부 서비스는 필요하지 않습니다.
기존 프로젝트에 `schema.sql`을 다시 실행할 필요는 없습니다.

마이그레이션은 기업 목록·제출 테이블과 조회/저장 RPC 두 개를 만듭니다.
기업 목록의 정본은 `public.moyeo_apply_companies`입니다. 화면은 API를 통해
이 테이블을 사용합니다. 기업 추가·이름 변경도 후속 SQL 마이그레이션으로
관리하며, 이미 선택에 사용된 기업 ID는 변경하거나 삭제하지 않습니다.

## 접근과 저장

- `/apply`는 기존 로그인 모달과 로그인 후 복귀 경로를 사용합니다.
- `GET /api/apply`와 `PUT /api/apply` 모두 세션을 확인하고, 사용자 JWT가
  연결된 Supabase 서버 클라이언트로 RPC를 호출합니다. 요청 본문에서 사용자
  ID나 수정 횟수의 새 값을 받지 않습니다.
- DB 함수는 `auth.uid()`로 사용자를 확인합니다. 미제출자와 미정이 남은 사용자의 목록 조회는
  `participants: null`이고, 5지망을 저장한 참여자에게만 지망·본인 여부와
  공개를 선택한 이름(비공개는 `이름 비공개`)을 반환합니다.
- 클라이언트 역할의 제출 테이블 직접 조회·추가·수정·삭제는 차단합니다.
  저장 함수가 기업 ID와 연속 순위를 검사하고, 사용자별 잠금 안에서 저장과
  수정 횟수 증가를 처리합니다. 최신 수정 횟수와 다른 변경 요청은 충돌로
  거절하며, 같은 내용을 다시 보내면 횟수를 쓰지 않습니다.
- 개인 응답은 `private, no-store`이며 상시 폴링은 하지 않습니다.

## 핵심 확인

[`supabase/tests/moyeo_apply.sql`](../supabase/tests/moyeo_apply.sql)은 테스트용
Supabase DB에서 마이그레이션 적용 후 실행할 수 있는 SQL 확인 스크립트입니다.
임시 사용자로 저장·재조회, 제출 전후 열람 권한, 2회 수정 한도와 직접 접근 차단을
검사하고 마지막에 롤백합니다. 운영 사용자나 실제 제출 자료로 테스트하지 않습니다.

배포 후에는 테스트 계정 두 개로 Google 로그인 복귀, 최초 제출 후 목록 공개,
두 번 수정 후 편집 잠금 및 계속 열람까지 확인합니다. 이 과정은 로컬 SQL 검증과
별개로 실제 Supabase 세션·배포 연결을 확인하는 절차입니다.

### 2026-10-06 구현 확인 결과

- 프로젝트 의존성을 바꾸지 않고 임시 PGlite 0.5.8(PostgreSQL 18.3)에서
  기존 프로필 마이그레이션, 새 마이그레이션과 위 SQL 검증을 실행해 통과했습니다.
  Supabase의 사용자 테이블과 `auth.uid()`만 최소 테스트 대역을 사용했습니다.
- 저장·재조회, 미제출자/제출자 열람, 2회 수정 제한, 변경 없음·실패·충돌 시
  횟수 보존, 비공개 필드 제외, 직접 조회·수정·삭제 및 익명 RPC 차단을 확인했습니다.
- TypeScript 검사와 변경한 TS/TSX 파일의 ESLint를 통과했습니다. 로컬 Chromium에서
  메뉴 진입, 비로그인 안내, 입력 폼·참여자 표 비노출, API 401 및 `no-store`를 확인했습니다.
- 편의 기능 추가 후 샘플 API 응답을 사용한 Chromium 화면에서 기업순 정렬,
  필터 결과 수·일치 기업 강조·초기화, 빈 순위를 만들지 않는 순위 교환과
  저장 전 요청이 발생하지 않는 것을 확인했습니다. 타입 검사와 ESLint도 통과했습니다.
- 운영 DB 마이그레이션 적용, 실제 Google 로그인과 로그인 후 API 저장 전체 흐름,
  여러 DB 연결에서의 동시 요청은 아직 확인하지 않았습니다.

### 2026-10-15 기업 선택 목록 변경

앱 변경과 함께 `20261015000000_moyeo_apply_company_options.sql`을 적용합니다.
Jido Labs와 기존 국가데이터처는 비활성화하고 국가데이터처(대전),
국가데이터처(서울), 국가데이터처(무차별)를 추가합니다. 선택 가능한 항목은
13개이며, 기존 제출 표시를 위해 API에는 비활성 항목도 `isActive: false`로
반환합니다. 입력·필터 목록은 활성 항목만 사용하고 DB는 비활성 항목의 저장을
거절합니다. 기업 목록 마이그레이션 자체는 기존 제출을 변경하지 않습니다.

`20261015010000_moyeo_apply_reset_edits.sql`은 기존 사용자 모두의 사용한
수정 횟수를 0으로 초기화해 남은 수정 기회를 2회로 만듭니다. 기존 지망과
석차는 보존하고, 초기화 전 편집 화면의 저장을 거절하도록 `updated_at`도
갱신합니다. 이 초기화는 한 번만 적용하며 사용자가 수정한 뒤 다시 실행하지 않습니다.

`20261015020000_moyeo_apply_move_nda_to_any.sql`은 기존 국가데이터처 지망을
같은 순위의 국가데이터처(무차별)로 옮깁니다. 지망 순서, 석차, 수정 횟수는
유지하고, 이전 편집 화면의 저장을 거절하도록 `updated_at`을 갱신합니다.
운영 적용 시점에 해당 제출은 5건이었고 무차별을 이미 고른 제출은 없었습니다.

### 2026-10-16 제출 완료 확정

앱 배포와 함께 `20261016000000_moyeo_apply_confirmation.sql`을 적용합니다.
기존 제출은 미확정으로 유지합니다. 등록자가 저장된 지망을 확인하고 최종
확정하면 참여자 목록에 제출 완료로 표시하고 지망·석차 수정을 잠급니다.
확정은 수정 횟수를 소비하지 않으며, 수정 기회가 0회여도 유효한 5지망이면
가능합니다. 확정 취소는 제공하지 않고 공식 신청과는 별개의 공유 상태입니다.

`POST /api/apply`는 본인의 `moyeo_apply_confirm` RPC만 호출합니다. 저장과
같은 사용자 잠금 및 수정 시각 검사를 사용하고 재시도는 멱등 처리합니다.
확정 시각은 본인에게만, 확정 여부는 기존 제출자 열람 권한 안에서 공개합니다.
확정 후 변경은 기존 저장 RPC에서도 거절하므로 구버전 화면으로 우회할 수 없습니다.


### 2026-10-18 미정 재참여와 이름 공개 선택

`20261018132648_moyeo_apply_reentry_name_privacy.sql`을 **앱 배포 전에** 적용합니다.
기존 RPC 서명은 유지하므로 이전 앱에서도 DB가 이름을 숨기고 미정 사용자의
목록 열람을 막습니다. 새 UI 배포 전까지는 이전 화면의 안내 문구가 다를 수 있습니다.
기존 브라우저에 이미 전달된 이름은 회수할 수 없으며, 탭 복귀나 새로고침으로
새 정책의 응답을 받습니다. 상시 폴링이나 공유 캐시는 추가하지 않습니다.

마이그레이션은 기존 지망·석차·확정 상태·수정 횟수를 삭제하거나 초기화하지
않고 이름 공개 여부를 모두 `false`로 시작합니다. `updated_at`은 갱신해 이전
편집 화면의 변경을 거절합니다. 미정 사용자는 자신의 기존 기록과
`requiresResubmission: true`만 받으며 참여자 목록은 받지 않습니다. 새 UI는
빈 폼에서 다시 입력하게 합니다. 완전한 5지망 재제출에 성공하면 수정 횟수는
0이 되며, 이후 정상 수정 2회와 최종 확정 규칙을 적용합니다.

`PATCH /api/apply`는 `moyeo_apply_set_name_visibility` RPC로 본인의 공개
설정만 변경합니다. 수정·확정과 같은 사용자 잠금 및 최신 수정 시각 검사를
사용합니다. 이름 공개는 수정 횟수나 확정 상태를 바꾸지 않습니다. 미공개
이름·사용자 ID는 참여자 응답에 포함하지 않으며 정렬에도 실제 이름을 쓰지
않습니다. 동률 정렬은 비공개 `private_sort_key`를 사용하며 사용자 ID와
연결되지 않습니다. API는 `privacyVersion: 1`이 없는 구버전 DB 응답을 503으로
차단합니다. 이름을 공개해도 석차 열람 조건은 그대로 적용합니다.

회귀 확인은 `supabase/tests/moyeo_apply.sql`, `moyeo_apply_confirmation.sql`,
`moyeo_apply_privacy.sql`을 임시 DB에서 실행합니다. 추가 검사는 기본 비공개,
숨긴 이름에 따른 순서 불변, 명시적 공개·비공개, 확정 후 공개 설정 변경,
오래된 요청 충돌, 미정 사용자 차단 및 수정 한도에서의 무료 재제출을 다룹니다.

로컬에서는 TypeScript·변경 파일 ESLint, 관련 테스트 14개, PGlite 0.5.8의
SQL 검사 4개 파일을 통과했습니다. 실제 `ApplyClient`를 jsdom에서 렌더링해
빈 재입력 폼, 저장 전 확인창, 재제출 시 기존 수정 시각 전달, 기본 비공개,
편집 중 공개 설정 잠금과 직접 공개 선택을 확인했습니다. 운영 DB 적용과
실제 로그인 세션을 통한 배포 환경 검증은 아직 수행하지 않았습니다.


2026-10-18 추가 보안 검토 결과는 [보안 점검 기록](MOYEO_APPLY_SECURITY_REVIEW.md)에
있습니다. `supabase/tests/moyeo_apply_security.sql`은 실제 프로필 RLS와 함께
익명 RPC·직접 테이블 접근·잘못된 배열·권한 및 함수 설정을 검사합니다.
