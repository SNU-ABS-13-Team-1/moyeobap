# 모여밥 데이터 구분과 평가기준 대응

> **문서 상태: 팀 합의(2026-08-12)**
>
> 2026-08-10~11 논의에서 나온 데이터 구분안을 팀이 받아들여 확정한 문서입니다.
> 세 구분은 코드에도 반영돼 있습니다 — ① `data/*.csv`와
> `app/data/restaurants.ts`, ② `app/lib/backend.ts`의 팟 상태,
> ③ `PotEvent`와 `GET /api/events`.
>
> **발표 자료에는 이 세 가지 데이터 구분 개념을 반드시 포함합니다.**

## 1. 왜 이렇게 나누는가

모여밥이 다루는 데이터를 **중요도**가 아니라 **서비스 안에서 만들어지고
활용되는 방식**에 따라 세 가지로 나눕니다. 세 데이터는 각각 서비스에서 맡는
역할이 다르고 평가기준에도 서로 다른 방식으로 기여하므로, 하나를 메인으로
정하고 나머지를 보조로 두지 않습니다.

| 구분 | 정체 | 서비스에서의 역할 |
|---|---|---|
| ① 외부 기준 데이터 | 서비스 외부에서 가져와 쓰는 데이터 | 탐색과 모집 시작의 기반 |
| ② 실시간 상태 데이터 | 특정 시점의 서비스 상태 | 지금 참여할 곳을 찾게 함 |
| ③ 행동/Event 데이터 | 이용 과정에서 누적되는 기록 | 선택을 돕는 정보로 재사용 |

## 2. 세 가지 데이터

### ① 외부 기준 데이터

- **무엇:** 음식점명, 위치, 메뉴처럼 서비스 외부에서 가져와 모여밥에서
  사용하는 데이터.
- **역할:** 사용자가 주변 음식점과 대표메뉴를 둘러보고, 원하는 음식점을
  선택해 모집을 시작할 수 있게 하는 기본 데이터.
- **생성 흐름:**

```text
화면 캡처
→ AI/OCR로 음식점·메뉴 정보를 구조화
→ 잘못 인식된 값 정제
→ 중복 음식점 제거
→ 카테고리 표준화
→ DB 저장
→ 웹에 표시
```

실제 수집·정제 규칙은 [data/DATA_GUIDE.md](../data/DATA_GUIDE.md)를 따릅니다.

### ② 실시간 상태 데이터

- **무엇:** 현재 모집 중인 음식점, 모집 인원, 참여 인원, 마감 시간 등 특정
  시점의 서비스 상태를 나타내는 데이터.
- **역할:** 지금 어디에서 몇 명이 같이 주문하려고 하는지 확인하고 바로
  참여할 수 있게 하는 모여밥의 핵심 기능.
- **생성 흐름:**

```text
모집 생성
→ 다른 사용자가 모집 확인
→ 참여
→ 참여 인원 변경
→ 모집 완료
```

### ③ 행동/Event 데이터

- **무엇:** 모집 생성·참여·취소·성공·실패·평가처럼 사용자가 서비스를
  이용하면서 발생하고 누적되는 기록.
- **역할:** 나중에 분석하려고 모으는 데이터가 아니라, 누적된 기록을 인기
  음식점·인기 메뉴 랭킹, 평점, 모집 성공률 같은 **실제 서비스 기능으로 다시
  제공**해 사용자의 선택을 돕는 데 활용.

## 3. 평가기준 대응

평가기준 원문:

1. 프로젝트가 의미 있는 문제를 명확하게 설정하고 있는가
2. 데이터 수집 및 정제 과정이 충실하게 이루어졌는가
3. 데이터와 전달하려는 메시지에 적합한 차트를 사용했는가
4. 인터랙티비티와 디자인이 사용자의 이해와 탐색을 돕는가
5. 프로젝트 결과물이 실제 웹 환경에 배포되어 정상적으로 작동하는가
6. 웹서비스의 기능, 구성 및 사용성이 완성도 있게 구현되었는가
7. AI를 활용한 구현 과정과 활용 방법을 구체적으로 설명했는가
8. 발표가 명확하고 프로젝트의 핵심 내용을 효과적으로 전달했는가

| 평가기준 | ① 외부 기준 | ② 실시간 상태 | ③ 행동/Event |
|---|:---:|:---:|:---:|
| ② 수집·정제 | ● | | ● |
| ③ 차트 | | | ● |
| ④ 인터랙티비티·디자인 | | ● | ● |
| ⑤ 배포·정상 작동 | ● | ● | |
| ⑥ 기능·구성·사용성 | ● | ● | ● |
| ⑦ AI 활용 설명 | ● | | |

### ① 외부 기준 데이터

- **②** 캡처를 통한 데이터 확보, 구조화, 오류 수정, 중복 제거, 표준화 과정을
  보여줄 수 있음.
- **⑦** 이미지에서 음식점 정보를 추출하고 구조화하는 데 AI/OCR을 어떻게
  활용했는지 설명할 수 있음.
- **⑥** 정제된 데이터를 DB에 저장하고 실제 음식점 탐색 및 모집 생성 기능에
  연결.
- **⑤** DB에 저장된 음식점 데이터가 실제 배포된 웹서비스에서 정상적으로
  조회되고 사용되는지 확인 가능.

### ② 실시간 상태 데이터

모집 생성 → 확인 → 참여 → 인원 변경 → 완료 흐름을 실제 웹에서 구현하면
**④ 인터랙티비티·디자인**, **⑤ 배포 및 정상 작동**, **⑥ 기능·구성·사용성**에
직접 연결됩니다.

### ③ 행동/Event 데이터

- **②** 서비스에서 발생하는 행동을 기록하고 목적에 맞는 형태로 저장·가공하는
  과정을 보여줄 수 있음.
- **③** 사용자에게 보여줄 필요가 있는 모집 현황이나 이용 정보를 적절한
  차트로 표현하는 데 활용.
- **④** 인기순·평점순, 랭킹, 평점 등의 정보를 통해 사용자가 음식점을 더 쉽게
  탐색하고 선택하도록 도움.
- **⑥** 누적된 행동 데이터를 랭킹·평점·모집 성공률 등 실제 서비스 기능으로
  다시 사용자에게 제공.

## 4. 문제 설정과의 연결 (평가기준 ①)

처음 해결하려던 문제는 점심시간마다 배달로 식사를 준비하는 과정의 불편함
입니다. 혼자 주문하면 배달비 부담이 크고, 주변에서 같은 음식점을 주문하려는
사람이 있는지 알기 어렵고, 같이 주문할 사람을 직접 찾고 조율하는 것도
번거롭습니다.

세 데이터는 이 문제 해결의 서로 다른 단계에 기여합니다.

- **외부 기준 데이터:** 주변에 어떤 음식점과 메뉴가 있는지 탐색하면서 동시에
  원하는 음식점을 선택해 모집을 시작할 수 있게 함.
- **실시간 상태 데이터:** 지금 어떤 음식점에서 모집이 진행 중인지, 몇 명이
  참여하고 있는지를 보여줘 같은 음식을 주문하려는 사람을 쉽게 찾고 참여할 수
  있게 함.
- **행동/Event 데이터:** 이용 기록을 축적하고 인기 음식점·인기 메뉴 랭킹,
  평점 등을 제공해 음식점과 메뉴 선택에 대한 의사결정을 돕게 함.

## 5. 발표에서 다룰 방식

세 데이터 중 무엇이 메인이고 무엇이 보조인지 나누지 않습니다. **우리가 정의한
문제를 해결하기 위해 각각 필요한 데이터를 목적에 맞게 수집·저장·활용하고,
그 과정이 평가기준에 어떻게 대응하는지**를 보여주는 순서로 구성합니다.

## 6. 아직 정하지 않은 것

- ③ 행동/Event 데이터를 어떤 차트로 보여줄지 (평가기준 ③)
- 랭킹·평점·모집 성공률의 산출 기준
- 데이터가 부족한 초기에 랭킹을 어떻게 표시할지
