# 알까기: 실시간 2인 대전

2026-08-26

## 무엇을 만드나

바둑돌을 손가락으로 튕겨 상대 돌을 판 밖으로 내보내는 알까기를 온라인 2인
대전으로 만든다. 돌은 5개씩, 상대 돌을 전부 내보내면 이긴다. 내 돌이 나가면
그 돌도 잃는다(자충수).

컴퓨터 대전은 만들지 않는다. 알까기 AI는 "어느 돌을 어느 각도·세기로 칠지"를
물리 시뮬레이션으로 탐색해야 해서 작업량이 게임 하나만큼 늘어난다.

## 왜 퐁이 아니라 오목을 닮는가

알까기는 물리 게임이지만 **턴제**다. 한 번 치면 돌이 굴러가다 멈추고, 그
다음에 상대가 친다. 퐁처럼 매 프레임 좌표를 방송할 이유가 없다.

| | 퐁 | 알까기 |
|---|---|---|
| 권위 | 방장 브라우저 | 서버 |
| 전달량 | 20Hz 좌표 방송 | 턴당 패킷 1개 (`{stoneId, vx, vy}`) |
| 방장이 나가면 | 판이 멈춘다 | 상관없다 |
| 관전자 난입 | 그 시점부터만 | 현재 배치가 DB에 있어 정확 |

그래서 `/move` 자리에 `/shoot`이 들어가는, 오목과 같은 서버 권위 구조로 간다.
치는 사람은 샷 세 값만 보내고, 서버가 턴·소유권을 검증한 뒤 시뮬레이션을 돌려
결과를 확정한다. 클라이언트는 같은 순수 물리 모듈로 굴러가는 장면을 그리고,
끝나면 서버가 준 최종 좌표로 스냅한다. 부동소수점이 미세하게 갈려도 화면과
정답이 어긋날 수 없다.

## 물리

`app/lib/alkkagiPhysics.ts` — DB도 렌더링도 모르는 순수 모듈. 서버와 클라이언트가
같이 import한다. 난수 없음, 돌 처리 순서는 id 정렬로 고정.

판은 640x640 논리 단위, 돌 반지름 26. 화면 크기와 물리를 분리해 창 크기가 달라져도
결과가 흔들리지 않게 한다. 시작 배치는 위아래 변에서 60 들어온 줄에 5개씩, 128 간격.

| 항목 | 값 | 근거 |
|---|---|---|
| 시뮬 간격 | 고정 1/240초 | 최대 속도에서 한 스텝 5단위 < 반지름 26 → 터널링 없음 |
| 감속 | 등감속 1100 단위/s^2 | 바둑돌은 미끄럼 마찰이라 지수감쇠보다 등감속이 맞다 |
| 최대 발사 속도 | 1200 단위/s | 최대 파워로 655단위를 굴러 판(640)을 겨우 가로지른다 |
| 정지 판정 | 8 단위/s 미만 | 그 아래는 0으로 스냅 |
| 충돌 | 같은 질량 탄성, 반발계수 0.94 | 법선만 교환하고 접선 유지 → 비껴 맞으면 얇게 튄다 |
| 안전장치 | 8초 초과 시 강제 정지 | 이론적 무한 튕김 방지 |

**판 밖 판정은 돌 중심 기준이다.** 가장자리에 반쯤 걸친 돌은 살아남는다. 벽은 없다.

`previewPath()`는 **첫 충돌 지점까지만** 반환한다. 끝까지 보여주면 정답을 읽고
클릭하는 게임이 된다. 첫 충돌까지만 보여주면 의도는 세울 수 있고 결과는 손끝에 남는다.

## 데이터

`supabase/migrations/20260907000000_add_alkkagi.sql` — 오목·바둑과 같은 4종
(`alkkagi_rooms` / `alkkagi_chat_messages` / `alkkagi_matches` / `alkkagi_ratings`).
쓰기는 전부 서버 `service_role`, 참여자만 SELECT(Realtime 구독용), 관전자는 폴링.
채팅에는 `kind`/이모티콘 컬럼을 처음부터 넣어 `GameChat`의 `emojis: true`를 바로 켠다.

`alkkagi_rooms`의 판 상태:

```sql
stones          JSONB   -- 살아있는 돌만: [{ id:"b0", owner:"black", x:64, y:580 }, ...]
pre_shot_stones JSONB   -- 직전 샷을 쏘기 "전"의 배치
last_shot       JSONB   -- { stoneId:"b2", vx:-430.5, vy:-1120.0 }
last_shot_at    TIMESTAMPTZ
shot_seq        INTEGER -- 샷마다 +1
```

`pre_shot_stones` + `last_shot`이 재생 필름이다. 떨어진 돌은 `stones`에서 빼므로
배열 길이가 곧 남은 돌 수다. `shot_seq`는 "이 샷을 이미 봤나"를 판단하는 표식이고,
새로고침했거나 중간에 들어온 사람은 seq만 맞춰두고 현재 배치부터 본다.

나머지 컬럼은 오목과 같다: `status(waiting|playing|finished)`, `black_*`, `white_*`,
`turn`, `winner(black|white|draw)`, `shot_count`, `started_at`, `turn_started_at`,
`rematch_by`.

## 턴 시계를 미래에 찍는 이유

내가 쏘는 순간 상대 차례가 시작되는데, 상대 화면에서는 돌이 아직 굴러가는 중이다.
그대로 두면 상대는 구경만 하다 시간을 뺏긴다. 서버는 시뮬레이션에서 정확한 정지
시각을 이미 알고 있으므로, `turn_started_at`을 "지금"이 아니라 **"돌이 다 멈추는
시각"(미래)** 으로 찍는다. 그러면 `isTurnExpired`/`remainingTurnMs`를 그대로
쓰면서도 시계가 공평해진다.

턴 제한은 45초. 오목(30초)보다 넉넉한 건 조준에 생각할 시간이 필요해서다.
`app/lib/alkkagiMatch.ts`에 두며 `badukMatch.ts`와 같은 모양이다.

## 승패

모든 돌이 멈춘 직후 서버가 한 번 판정한다.

- 상대 0개, 나 1개 이상 → 내 승
- 둘 다 0개 → 무승부 (마지막 돌끼리 같이 떨어진 경우)
- 나 0개, 상대 1개 이상 → 상대 승 (자충수로 자멸)

랭킹은 주간제다. `alkkagi_ratings`에 `week_key`를 넣어 `(user_id, week_key)`
기본키로, 월요일마다 1200에서 다시 시작하고 지난주 top 3는 명예의 전당에 남는다
(오목·체스·퐁·루미큐브와 같은 방식. 바둑만 통산 누적인데 다수를 따랐다).

## 화면과 조작

레이아웃은 오목과 같은 2단 — 왼쪽 판, 오른쪽 채팅. 상단에 방 이름·관전자·
플레이어·상태·시계, 그리고 알까기용으로 남은 돌 수 한 줄(`⚫ 5 — 4 ⚪`).

**내 진영은 항상 아래쪽이다.** 백을 잡은 사람에게는 판을 180도 돌려 그린다.
알까기는 "위로 밀어낸다"는 방향감이 조작의 전부라, 내 돌이 위에 있으면 드래그
방향이 계속 헷갈린다. 관전자에게는 흑이 아래. 뒤집기는 그리기·입력 좌표 변환
한 곳에서만 하고, 물리와 DB는 언제나 흑이 아래인 원본 좌표만 쓴다.

조준은 끌어서 놓기다. 포인터 이벤트로 처리해 트랙패드·마우스·터치가 같은 코드로
동작한다.

1. 내 차례에 내 돌을 누른다(반지름보다 넉넉한 범위로 집기 쉽게)
2. 반대 방향으로 끈다 → 끈 거리가 파워, 끈 반대 방향이 발사 방향. 포인터 좌표는
   먼저 논리 좌표로 환산하고, 최대 끌 거리 213 논리 단위(화면 480px 기준 약 160px)에서 파워 100%
3. 끄는 동안 발사 방향 화살표 · 파워 게이지 · 첫 충돌까지의 예측 점선이 보인다
4. 놓으면 발사. 돌 위로 되돌리면(16 논리 단위 이내) 취소

**놓는 즉시 내 화면에서 굴러가기 시작하고, 동시에 `POST /shoot`을 보낸다.**
왕복 지연을 기다렸다 굴러가면 손맛이 죽는다. 물리가 결정적이라 서버 결과와
어긋나지 않고, 서버가 거절하면(시간 초과 등) 애니메이션을 접고 현재 배치로
되돌린 뒤 사유를 띄운다.

상대 화면은 Realtime UPDATE로 `shot_seq`가 오른 걸 보고 `pre_shot_stones`부터
재생하되, `last_shot_at`을 보고 **이미 지난 시간만큼 건너뛰고 이어서** 그린다.
네트워크가 느렸다고 상대 화면에서만 늦게 도착하는 일이 없어진다.

판 밖으로 나간 돌은 그 자리에서 사라지지 않고 계속 미끄러져 나가며 작아지고
흐려진다. 애니메이션이 도는 동안은 조작을 잠근다.


캔버스 애니메이션까지 얹혀 한 파일이 1000줄을 넘기 때문이다.

재사용하는 것(새로 만들지 않음): `gameSeats.ts`, `GameLobby`·`GameChat`·
`GameRanking`, `gameHall.ts`, `Spectators`, `AuthProvider`, `fetcher`/`api-client`.

수정하는 것: `app/games/page.tsx`(게임 목록), `openRooms.ts`(+test),
`app/api/games/rooms/route.ts`("지금 열려있는 방" 합류), `prototype.css`.

## 동시성

`/shoot`은 읽고-계산하고-쓰는 사이에 상대 요청이 끼어들 수 있다. 저장할 때
**`shot_seq`와 `turn`을 조건으로 건 UPDATE**를 써서, 조건이 안 맞으면 0행이
갱신되고 요청이 거절되게 한다. 같은 턴에 두 번 쏘거나 시간 초과 처리와 발사가
겹쳐 판이 꼬이는 일을 막는다(루미큐브에서 한 번 겪은 종류의 문제다).

## 예외 처리

기존 게임 규칙을 그대로 따른다: 한 명이 나가면 방은 남고 자리만 비운다 →
관전자가 앉으면 재개 / 대국 중 이탈은 기권패 / 상대 접속이 끊기고 60초 지나면
몰수승 버튼 / 24시간 멈춘 방은 상태와 무관하게 정리 / 재대국은 흑백 교대.

## 검증

`npm run test` → `npm run lint` → `npm run typecheck` → `npm run build`.

물리는 순수 모듈이라 테스트로 잡힌다(정면으로 맞히면 맞은 돌이 나가고 친 돌이
거의 선다 / 판 끝으로 민 돌은 제거되고 걸친 돌은 남는다 / 같은 입력은 항상 같은
결과 / 8초 안에 반드시 모두 정지). 다만 **손맛은 테스트로 안 잡히므로**, 구현
뒤 실제로 띄워 쳐보고 감속·반발계수를 조정하는 단계를 계획에 넣는다.
