## 1. 기술 스택 선정 이유 관련

### Q1. "왜 Spring Boot나 Express 대신 Next.js + Supabase 조합을 선택했나요?"
- **1줄 요약**: "빠른 프로토타이핑과 실시간 협업 기능, 프론트/백엔드 타입 일관성을 위해 Next.js 풀스택 + Supabase BaaS 조합을 선택했습니다."
- **상세 답변**:
  - **Next.js 16 (App Router)**: 프론트엔드 UI와 API 엔드포인트(`/api/stats` 등)를 TypeScript 하나로 통합 개발하여 타입 안정성을 확보하고, Vercel과의 연계를 통해 `git push`만으로 무중단 자동 배포(CI/CD) 파이프라인을 구축했습니다.
  - **Supabase**: 별도의 백엔드 인프라 구축 비용을 줄이고, 검증된 **PostgreSQL 관계형 DB**, **Google OAuth 인증**, **Realtime WebSocket 푸시**를 즉시 활용하여 2주 남짓한 프로젝트 기간 동안 핵심 비즈니스 로직(실시간 팟 조율)에 집중할 수 있었습니다.

### Q2. "데이터베이스는 어떤 걸 썼고, 데이터 모델링은 어떻게 구성했나요?"
- **1줄 요약**: "Supabase 기반의 **PostgreSQL** 관계형 데이터베이스를 사용했습니다."
- **상세 답변**:
  - `pots`(팟 정보: 식당, 마감시간, 상태, 관리자ID), `participants`(참여자 관계 테이블), `messages`(팟 대화/계좌공유) 등으로 관계를 정규화하여 설계했습니다.
  - 고정된 식당 112곳과 메뉴 548개의 **기준 데이터는 빌드 시 프론트에 내장(`restaurants.ts`)**하여 DB 부하를 원천 차단했고, 동적으로 변하는 **실시간 팟/채팅 데이터만 PostgreSQL**에서 트랜잭션으로 처리합니다.

## 2. 실시간 동기화 (Realtime) & 성능 관련 (★ 가장 중요한 질문!)

### Q3. "실시간 기능은 전부 웹소켓(WebSocket)으로 구현했나요?"
- **1줄 요약**: "아닙니다. 데이터 특성에 맞춰 **웹소켓 푸시와 폴링(Polling)을 적절히 혼합한 이중화 구조**를 적용했습니다."
- **상세 답변**:
  - **팟 채팅(`messages`)**: 즉각적인 반응이 필요하므로 **Supabase Realtime Channel(WebSocket)**로 `INSERT` 이벤트를 실시간 푸시하되, 네트워크 순단에 대비해 **3초 주기 폴링을 fallback으로 이중화**했습니다.
  - **현황판 & 팟 상세**: 불필요한 상시 소켓 커넥션 비용을 줄이기 위해 **4초 주기 경량 폴링**으로 최신 상태를 동기화합니다.
  - **식사 트렌드(`/trends`)**: 집계 API 부하를 고려해 **10초 주기 폴링**으로 갱신됩니다.
  - **낙관적 UI(Optimistic UI)**: 채팅 전송 시 서버 응답을 기다리지 않고 화면에 즉시 렌더링하여 사용자 체감 딜레이를 0으로 만들었습니다.

### Q4. "트렌드 페이지의 통계 수치(성사 시간, 랭킹 등)는 어떻게 계산되나요?"
- **1줄 요약**: "미리 만들어둔 정적 데이터가 아니라, **Next.js API Route(`/api/stats`)에서 누적된 팟 이력을 요청 시점에 실시간 집계**합니다."
- **상세 답변**:
  - 사용자가 팟을 생성하고 참여하고 마감할 때마다 PostgreSQL에 쌓이는 실제 이력 데이터를 서버 함수(`getCampusStats`)가 집계합니다.
  - 따라서 발표 중 청중이 실시간으로 팟을 열고 참여하면 트렌드 그래프와 순위 수치도 실시간으로 반영됩니다.

## 3. 보안 및 사용자 인증 관련

### Q5. "사용자 인증과 개인정보(특히 정산 계좌번호) 보안은 어떻게 처리했나요?"
- **1줄 요약**: "Supabase Auth(Google OAuth)를 사용하며, 계좌번호는 DB 공개 테이블이나 전역 상태에 노출되지 않도록 철저히 격리했습니다."
- **상세 답변**:
  - **인증**: 별도의 비밀번호 저장 없이 Google OAuth 토큰 기반으로 안전하게 인증하며, 내부 식별자는 이메일이 아닌 Supabase `auth.users.id`(UUID)를 사용합니다.
  - **계좌번호**: 회원가입 필수 항목이 아니며, 본인이 프로필에 등록하더라도 공개 API에 포함되지 않습니다. **오직 본인이 팟 채팅방에서 '계좌 공유' 버튼을 눌러 메시지로 전송했을 때만 해당 팟 참여자에게만 노출**됩니다.

## 4. 아키텍처 및 서비스 범위 관련

### Q6. "왜 배달의민족처럼 메뉴 장바구니/결제까지 직접 구현하지 않았나요?"
- **1줄 요약**: "주문/결제는 이미 배민의 '함께주문' 기능이 잘하므로, 저희는 **'누구도 먼저 제안하지 않는 침묵'과 '주문 직전 사람을 모으는 마찰'을 해결하는 것에 집중**했습니다."
- **상세 답변**:
  - 메뉴 선택 및 PG 결제 대행을 직접 구현하면 가맹점 제휴 및 정산 책임 등 서비스 본질과 다른 복잡도가 발생합니다.
  - 모여밥은 **"인원 모집 ➔ 마감 ➔ 조율 ➔ 배민 함께주문 링크로 원클릭 인계"**까지만 책임지는 명확한 Scope(범위)를 설정해 사용성을 극대화했습니다.

---

### Q7. "팟 관리자가 도중에 나가버리면 팟은 어떻게 되나요?" (상태 머신 질문)
- **1줄 요약**: "**참여 순서 기준 자동 관리자 승계 알고리즘**을 적용해 방이 주인 없이 방치되지 않도록 설계했습니다."
- **상세 답변**:
  - 최초 팟 생성자가 관리자가 되지만, 관리자가 참여를 취소하면 남은 참여자 중 **`created_at`(참여 시각)이 가장 빠른 사람에게 관리자 권한이 자동 이전**됩니다.
  - 참여자가 1명뿐인 상태에서 마감 시각에 도달하면 자동으로 `failed(실패)` 종료 처리되어 고아 팟이 남지 않습니다.

## 5. 데이터 엔지니어링 관련

### Q8. "식당 112곳, 메뉴 548개 데이터는 어떻게 수집/구축했나요?"
- **1줄 요약**: "불법 크롤링 대신 **팀원들이 직접 캡처한 화면을 AI OCR로 초안 추출 후, 사람의 11항목 검수를 거치는 'Human-in-the-loop' 파이프라인**으로 구축했습니다."
- **상세 답변**:
  - 캡처 시 개인정보 영역을 마스킹하고 원본은 전사 후 폐기하는 데이터 가이드를 준수했습니다.
  - AI OCR의 텍스트 잘림·오인식을 팀원들이 엑셀 템플릿으로 교차 검수한 뒤 `scripts/xlsx_to_csv.py` 스크립트를 통해 최종 정본 CSV로 변환하여 서비스에 탑재했습니다.

## 6. 추가 심층 기술 질문 (돌발 질문 대비)

### Q9. "동시성 이슈(예: 정원 4명인 팟에 2명이 동시에 참여 버튼을 누름)는 어떻게 방지했나요?"
- **1줄 요약**: "클라이언트 단의 중복 클릭 방지와 서버 API에서의 트랜잭션/정원 검증 로직으로 제어했습니다."
- **상세 답변**:
  - `app/api/pots/[id]/join/route.ts`에서 참여 요청 수신 시, 현재 팟의 상태가 `active`인지와 `max_participants` 정원 초과 여부를 서버 측에서 즉시 재검증한 후 DB 트랜잭션으로 참여자를 추가합니다.

### Q10. "AI 개발 도구와의 협업에서 기획/규칙 충돌은 어떻게 해결했나요?"
- **1줄 요약**: "`AGENTS.md`를 단일 진실 공급원(Single Source of Truth)으로 두고, 기획·아키텍처 규칙을 문서화하여 AI가 일관된 코드를 작성하도록 통제했습니다."
- **상세 답변**:
  - 구두 프롬프트에 의존하지 않고, 데이터 3분류 원칙과 상태 전이 규칙을 `AGENTS.md`에 명시해 모든 AI 세션이 동일한 지침을 참조하도록 강제했습니다.
